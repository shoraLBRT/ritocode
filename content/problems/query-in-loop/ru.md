  Запрос к базе или внешнему API делается на каждой итерации цикла, вместо одного запроса на все
  элементы (проблема N+1). Одна загрузка всех данных без лимита — это «Всё в память».
keywords: [N+1, запрос в цикле, select в цикле, API в цикле, ORM, lazy loading, медленно]

## Signs

- Внутри `for order in orders:` вызывается `get_customer(order.customer_id)`, который ходит в базу.
- Обращение к связанному полю ORM в цикле, которое незаметно делает отдельный запрос.
- HTTP-запрос к внешнему сервису на каждый элемент списка.
- Время работы растёт вместе с числом записей, хотя сама обработка простая.

## Why AI does it

Код пишется так, как формулируется задача: «для каждого заказа найди клиента». На тестовых пяти
записях пять запросов незаметны, а сколько записей будет на самом деле, агенту не сказали.

## Cost

- Страница или отчёт работают в сотни раз медленнее, чем могли бы, и тормозят тем сильнее, чем
  больше данных.
- База и внешний API получают лишнюю нагрузку; платный API выставляет счёт за каждый запрос.
- Ограничение частоты внешнего API срабатывает, и часть данных тихо не загружается.

## Acceptable when

- Элементов заведомо единицы и их число не растёт.
- Разовый скрипт, где время работы не важно.

## Detection

Подсчёт запросов в тестах с порогом; журнал запросов ORM в разработке; мониторинг производительности
в продакшене.

## Treatment

Загрузить всё нужное одним запросом — через соединение таблиц, `IN` по списку идентификаторов или
пакетный вызов API; сказать агенту ожидаемый объём данных.
Неправильное лечение — добавить кэш вокруг запроса в цикле.

## Counter-arguments

Иногда отдельные простые запросы с кэшем на стороне базы работают не хуже одного сложного
соединения. Решает замер, а не правило.
